# Fonteyn Holidayparks - Cloud Infrastructure Administration Guide

**Version:** 1.0  
**Last Updated:** January 5, 2026  
**Audience:** System Administrators & Operations Team

---

## 1. Executive Summary & Transformation Goals

Fonteyn Holidayparks has transitioned from a fragmented, on-premise infrastructure to a centralized, scalable cloud solution on Microsoft Azure.

### The "Before" State (Legacy Issues)
*   **Fragmented Network:** Parks operated in isolation; data was not easily shared.
*   **Single Point of Failure:** Services were hosted locally. If a park lost power or internet, critical services went down.
*   **Data Loss:** Files were frequently lost due to lack of centralized storage.
*   **High Maintenance:** Manual updates and server patching required significant IT effort.

### The "After" State (Cloud Solution)
*   **Centralized & Connected:** All services run in the Azure Cloud, accessible from any park or remote location.
*   **High Availability:** The system is no longer dependent on local hardware. Azure guarantees high uptime.
*   **Scalable:** The infrastructure automatically adjusts to demand (e.g., high traffic during holiday booking seasons).
*   **Secure & Automated:** Automated pipelines handle deployments, security scanning, and updates.

## 2. System Architecture Overview

The new solution utilizes modern "Serverless" and Container technologies to minimize upkeep.

### Core Components

| Component | Azure Service | Role & Benefit |
| :--- | :--- | :--- |
| **Customer Website** | Azure Container Apps | Hosts the public-facing booking site. Scales automatically to zero or up to meet demand. |
| **Customer API** | Azure Container Apps | Handles business logic and data processing. Decoupled from the frontend for flexibility. |
| **Database** | Azure SQL Database | Centralized relational database. Fully managed (no OS patching required) with automated backups. |
| **File Storage** | Microsoft SharePoint | Replaces local file servers. Ensures documents are versioned, searchable, and never lost. |
| **Security/Secrets** | Azure Key Vault | Securely stores database passwords and API keys. No sensitive data is hardcoded in scripts. |
| **Monitoring** | Azure Log Analytics | Centralized logging for all apps. Provides a single dashboard for troubleshooting. |
| **Images** | Azure Container Registry (ACR) | Stores the secure, versioned Docker images used by the Container Apps. |

## 3. Deployment & Updates (CI/CD)

We have moved away from manual file copying. All updates are handled via an automated **Azure DevOps Pipeline**.

### The Pipeline Flow
1.  **Code Change:** Developers push code to the repository.
2.  **Automated Checks (Stage: Test):**
    *   **Linting:** Checks for code errors.
    *   **Security Scan:** Scans for vulnerabilities (Bandit).
    *   **Dependency Audit:** Checks for unsafe libraries.
    *   *If any check fails, the process stops immediately.*
3.  **Approval Gate (Stage: ApproveBuild):**
    *   The pipeline **pauses** here.
    *   **Action Required:** A System Admin must approve the build in the Azure DevOps portal.
    *   This is your "Go/No-Go" control point.
4.  **Build & Push:** Docker images are built and stored in ACR.
5.  **Deployment:** The Container Apps are updated with the new images automatically.

### Admin Responsibility
*   **Monitor Notifications:** You will receive an email when a deployment is waiting for approval.
*   **Review:** Check the "Test" stage logs if needed before clicking "Approve".

## 4. Operational Management & Troubleshooting

### Monitoring System Health
Instead of checking individual servers, use **Azure Log Analytics**:
1.  Navigate to the **Log Analytics Workspace** in the Azure Portal.
2.  Use Kusto Query Language (KQL) to query logs across the Website and API.
3.  **Common Scenario:** If a user reports a "500 Error", query the `ContainerAppConsoleLogs_CL` table to see the exact error message generated by the application.

### Managing Secrets
**NEVER** store passwords in text files or code.
1.  Go to **Azure Key Vault**.
2.  Select **Secrets**.
3.  Update values here (e.g., Database Connection Strings). The Container Apps are configured to pull these values automatically upon restart.

### Database Maintenance
Azure SQL Database is a Platform-as-a-Service (PaaS):
*   **Backups:** Automated Point-in-Time Restore is enabled by default.
*   **Performance:** Use the "Query Performance Insight" tab in Azure Portal to see if any queries are slowing down the system.

### File Sharing (SharePoint)
*   All business documents are now stored in the corporate SharePoint site.
*   **Benefit:** This enables real-time collaboration and version history, eliminating the "lost file" problem of the old local servers.

## 5. Disaster Recovery & Scalability

### What happens if a Park loses power?
*   **Service Continuity:** The Website and API remain **100% operational** because they run in Azure, not at the park.
*   **Access:** Staff can access the system via 4G/5G or from another location.

### What happens during peak booking season?
*   **Auto-Scaling:** Azure Container Apps are configured with **KEDA** (Kubernetes Event-driven Autoscaling).
*   **Behavior:** As traffic increases, Azure automatically spins up more instances of the Website/API. When traffic drops, it scales down to save costs.
*   **No Admin Action Required:** This process is fully automated.
